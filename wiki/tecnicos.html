Documentación técnica

Para desarrolladores e IT · fuente de verdad: el repo — ESTRIN217/Terminal (detalles en AGENTS.md y docs/constitution.md).

Esta página condensa lo que un desarrollador o un equipo de IT necesita para compilar, entender la arquitectura, depurar y contribuir al fork. Va al código y a su proceso: para el uso del producto mira las demás páginas, y hacia las recetas del guest (X11, USB, Android Studio) solo se enlaza cuando hace falta.

La pila, de un vistazo

Qué es
App Android de terminal + entorno Linux (Debian vía proot, sin root), UI en Jetpack Compose y emulación de terminal nativa (JNI pty).
Toolchain
JDK 17 · NDK 30.0.14904198 · CMake 3.31.6 · Gradle 9.7.1 · AGP 9.4.1 · Kotlin 2.4.20 · Compose BOM 2026.09.00
SDK
minSdk 26 (Android 8.0), código nativo compilado contra android-28. El targetSdk 28 es intencional: subirlo activa scoped storage y otras restricciones que rompen el modelo de acceso a ficheros.
ABIs
arm64-v8a únicamente: el binario proot (loader + ensamblador AArch64) está portado solo a ARM64 y no se soportan otras ABIs en runtime.
Paquete
com.estrin217.terminal con UID compartido com.termux: toda la familia de APKs de la firma debe firmarse con la misma key.

Arquitectura de módulos

app  →  termux-shared  →  terminal-view  →  terminal-emulator
  └─→  filemanager  →  termux-shared
Módulo Paquete Propósito
terminal-emulator com.termux.terminal Motor de emulación VT100/xterm, pty por JNI. Cero dependencias internas.
terminal-view com.termux.view Renderizado como View de Android para la terminal.
termux-shared com.termux.shared Lógica compartida: settings, utilidades de ficheros, sistema de errores, crash handling, constantes.
filemanager com.estrin217.filemanager Librería reutilizable del gestor: FileOperationsHelper, FileSortOption, Compose FileManagerScreen/FileManagerViewModel. Java + Kotlin (Compose), con sus propios string resources.
app com.termux Activities, services y punto de entrada. Java + Kotlin (Compose).

¿Dónde toco qué?

  • Bug de emulación VT100/xterm: terminal-emulator.
  • UI/Activities: app.
  • Cuestión transversal (settings, errores, ficheros): termux-shared.

Reglas de dependencia

  • terminal-view expone terminal-emulator vía api() (transitivo). No cambiar a implementation() sin entender el impacto en los consumidores.
  • terminal-view no puede declarar dependencias hacia termux-shared: esa dirección crearía un ciclo.
  • Utilidad que termux-shared y también terminal-view o terminal-emulator necesitan → se implementa en terminal-emulator y se delega desde la clase original (p. ej. TerminalUrlScanner), conservando su API pública para no tocar a los callers.
  • El host del gestor de ficheros vive en app: FileManagerSessionHost aloja FileManagerScreen como pestaña de sesión, y los permisos de almacenamiento, FileProvider y el tema se cablean en la app.

Lenguaje, estilo y patrones

Java + Kotlin

  • Librerías terminal-emulator, terminal-view, termux-shared son Java puro: no añadir ficheros Kotlin ahí. La única librería con Kotlin es filemanager.
  • El módulo app usa Kotlin para la capa Compose (paquete com.termux.terminal.compose, punto de entrada TermuxComposeActivity.kt); activities/services existentes siguen en Java.
  • Notación húngara en Java y Kotlin: mTermuxService, mIsVisible.
  • Toda clase define LOG_TAG arriba (campo static final en Java, companion object en Kotlin).
  • Clases concretas final; Javadoc/KDoc en métodos públicos con @param/@return y {@link ...}.
  • Constantes centralizadas en TermuxConstants.java (~1357 líneas): rutas, acciones de intent y extras. Nada disperso por los ficheros.
  • Identificadores y comentarios técnicos en inglés; el texto visible del usuario va en strings.xml (EN, values-es-rVE, values-pt-rBR), nunca literal en Compose.

Manejo de errores

  • Se devuelven objetos Error, no se lanzan excepciones. null significa éxito:
Error error = TermuxFileUtils.isTermuxFilesDirectoryAccessible(ctx, true, true);
if (error != null) {
    Logger.logErrorExtended(LOG_TAG, "Failed\n" + error);
    return;
}
  • La clase Errno define los códigos (ERRNO_SUCCESS, ERRNO_CANCELLED, ERRNO_FAILED); usar las factorías Errno.getError().
  • Try/catch dirigido: se capturan excepciones concretas (IOException, BadTokenException), se registra con Logger, se notifica con Toast y se marca el flag de estado (p. ej. mIsInvalidState).
  • CrashHandler (excepciones no capturadas) escribe el crash log y avisa a la app por broadcast; se instala en TermuxApplication.onCreate().
  • Registro con com.termux.shared.logger.Logger, nunca android.util.Log directo: Logger trocea mensajes largos respetando el límite de logcat de 4068 bytes.

Patrones

  • Client Interface Pattern: las interfaces definen contratos (TerminalSessionClient, TerminalViewClient); bases con no-op por defecto (TermuxTerminalSessionClientBase); implementaciones concretas en app extienden las bases.
  • Ciclo de vida del servicio: TermuxService sobrevive a TermuxComposeActivity (rotación, reinicio, re-bind). No guardar referencias de la Activity en el service — pasar por la interfaz client.
  • Utilidades estáticas para helpers sin estado (TermuxUtils, TermuxThemeUtils, DataUtils).
  • Pestañas de sesión polimórficas (Compose): TermuxSessionUiModel es un sealed type (Terminal = sesión pty, FileManager = sesión solo de UI). Cerrar la pestaña del gestor de ficheros no toca TermuxService.
  • Delegación hacia abajo: la lógica compartida por módulos bajos vive en el fondo del grafo (terminal-emulator) y los módulos de arriba delegan — ver reglas de dependencia.

Internals: proot y Debian rootfs

Binario proot
Pipeline CMake multi-stage (loader → strip → objcopy → loader-info → proot final) empaquetado en app/src/main/assets/arm64-v8a/proot. Las tareas merge.*Assets dependen de buildCMake para garantizar que el binario esté en el APK en el primer build.
Rootfs Debian
Se descarga en el primer arranque (no en build time) vía DebianInstaller.java con verificación SHA-256 en streaming. El viejo task Gradle downloadBootstraps fue eliminado — el stack Compose usa commons-compress para extraer el rootfs y HttpURLConnection directo para el HTTP (no hay Ktor).
UID compartido
Toda la familia com.termux comparte UID Linux: los APKs deben firmarse con la misma key.

El subsistema USB sin root (lsusb/termux-usb vía API de Android, resolución de volúmenes con bind -b /storage:$HOME/storage porque SELinux deniega el readdir de /storage, no el del hijo) y sus límites están documentados en Limitaciones conocidas. Detalle completo en las specs cerradas 020 y 021 del repo.

Compilar y probar

./gradlew assembleDebug
./gradlew test              # todos los módulos, tests unitarios
./gradlew :filemanager:test # módulo filemanager por separado
  • JDK 17 obligatorio: los builds fallan con versiones anteriores.
  • NDK 30.0.14904198 y CMake 3.31.6 en local y CI; el código C nativo de terminal-emulator, termux-shared y app lo consume.
  • JitPack usa NDK 29.0.14206865 vía env JITPACK_NDK_VERSION: la divergencia con el NDK local/CI (30) es esperada, no un bug.
  • El único gate de calidad es ./gradlew test: NO hay lint, detekt, ktlint ni formatter configurados.
  • El versionName debe seguir semver major.minor.patch; la validación vive en app/build.gradle.kts y la versión en curso se imprime con ./gradlew :app:versionName.
  • Instrumented tests: no hay en CI; solo tests unitarios JUnit.

Splits ABI: por defecto los builds debug generan arm64-v8a + universal, controlado por la variable de entorno TERMUX_SPLIT_APKS_FOR_DEBUG_BUILDS. La release es de arm64-v8a únicamente.

CI y firma

Workflow (.github/workflows/) Qué hace
debug_build.yml Build (push a master, PRs): valida SemVer, compila assembleDebug, valida APKs (universal/arm64-v8a) y sube artefactos con sha256sums.
run_tests.yml Unit tests: gate de tests en CI.
attach_debug_apks_to_release.yml Adjunta los APKs debug de la última release de GitHub.
dependency-submission.yml Automatic Dependency Submission: genera y envía el grafo de dependencias del proyecto al Dependency Graph de GitHub.
gradle-wrapper-validation.yml Verifica el wrapper de Gradle contra la firma oficial.
trigger_library_builds_on_jitpack.yml Dispara el build de las librerías en JitPack (con NDK 29 por env).

Firma

  • Los secretos van en key.properties (nunca en el repo). El UID compartido com.termux exige que todas las APKs del proyecto se firmen con la misma key.

Publicación del sitio y de la wiki

  • firebase.json define dos targets de Hosting: main (dir public/, sitio con descarga y requisitos) y terminal-gnulinux-docs (dir wiki/, esta documentación estática).
  • Los datos del sitio que caducan (versión, fecha, tamaño, SHA-256, enlaces del APK) NO se escriben a mano: los pone scripts/update-site.py, que lee la última release de la API de GitHub y solo procesa public/index.html. Es idempotente y tiene --dry-run.
  • La wiki y los 404 no llevan versión ni datos que caducan horneados: no necesitan update-site.py.
  • Cache-Control: no-cache en ambos targets: los cambios de contenido se ven al refrescar.

Depuración y soporte

  • Logcat: filtra por el LOG_TAG de la clase que interesa (p. ej. adb logcat -s ClassName). Los mensajes largos los trocea Logger; si la primera línea se corta, busca la continuación del mismo tag.
  • Crashes: CrashHandler escribe el crash log en fichero y notifica a la app por broadcast: revisar ese log antes de abrir un issue.
  • Errores: los objetos Error incluyen el mensaje extendido completo — al reportar, pégalo tal cual (el detalle suele estar ahí, no lo resumas).

Los issues se abren en ESTRIN217/Terminal, nunca a los canales de Termux: es un fork independiente sin afiliación con el equipo de Termux.

Contribuir

  • Spec-Driven Development: sin specs/NNN-*/ aprobada no hay cambio de comportamiento; lee docs/constitution.md y la spec activa antes de tocar código. Si el código contradice la spec, se corrige la spec antes que el código; cada tarea implementada referencia su requisito funcional (RF).
  • Tests primero: test en rojo, luego código. ./gradlew test en verde antes de marcar la tarea como hecha.
  • Lógica fuera de la UI: parseo, split y cálculos van en funciones puras con test JUnit que corre sin Android; Compose y las Views solo pintan y despachan.
  • Commits: Conventional Commits con el tipo inicial en mayúscula: Added, Changed, Deprecated, Removed, Fixed, Security.

Gotchas con historial (salidos de specs cerradas): al tocar un bloque de prefs persistidas, conserva todas sus keys — refactorizar el serializador y soltar una key pierde el ajuste en silencio (lección de la spec 008; claves del gestor: sort_option, sort_ascending, show_hidden, folders_first, view_mode, favorites) — y no subas el targetSdk 28.

El detalle completo (constitución, gotchas con ejemplos, reglas por módulo) está en AGENTS.md y docs/constitution.md del repo; las guías por página van en el índice lateral, y la receta de Android Studio ARM64 —con el parche skiko incluido— en Android Studio (ARM64).
